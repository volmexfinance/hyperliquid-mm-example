# Hyperliquid HIP-3 API notes (`bart:AAPL` testnet, `mkts:BVIV` mainnet)

Verified against the official Hyperliquid API docs, installed `hyperliquid-python-sdk==0.24.0`, upstream SDK source, and read-only testnet API queries on 2026-09-23.

## DEX metadata and asset ID

- HIP-3 perp names use `{dex}:{coin}`. The current testnet `perpDexs` response put `bart` at index 87; its `meta(dex="bart")` universe put `bart:AAPL` at index 8. The resulting raw asset ID is `100000 + 87 * 10000 + 8 = 970008`. Resolve these indexes dynamically; do not bake them into orders. [Asset ID docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/asset-ids) · [perpetual metadata docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/perpetuals)
- Initialize the official SDK `Info`/`Exchange` with `perp_dexs=["bart"]`. The SDK loads the HIP-3 universe and maps `bart:AAPL` to the asset ID. The bot checks its map against the runtime metadata-derived ID before signing. [`Info.__init__` / `set_perp_meta`](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/info.py) · [`Exchange.__init__`](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/exchange.py)
- The 2026-09-23 testnet metadata reports `szDecimals: 2`, `maxLeverage: 5`, `marginMode: "strictIsolated"`, `onlyIsolated: true`, and `marginTableId: 5`; collateral token index `0` resolves through `spotMeta` to USDC. These values can change at runtime, so both bots re-read DEX metadata and do not assume 10x or cross margin. [Perpetual info docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/perpetuals)
- `Exchange.update_leverage(leverage, name, is_cross=...)` signs `updateLeverage` using the SDK's current asset map. The bots set `is_cross=false` for isolated-only metadata, acknowledge leverage on startup, and on a tier rejection, then retry the rejected order once. [Update leverage docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint) · [SDK implementation](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/exchange.py)

## Oracle, mid, and book

- `metaAndAssetCtxs` accepts a `dex` field. The bot posts `{ "type": "metaAndAssetCtxs", "dex": "bart" }` and reads `oraclePx` from the context matching the asset's index in the returned `meta.universe`. The SDK's `Info.meta_and_asset_ctxs()` omits a dex parameter, so this request uses the base `Info.post` method. The bot defaults `--ref oracle`; `--ref mid` instead reads `{ "type": "allMids", "dex": "bart" }` and selects `bart:AAPL`. [Perpetual info docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/perpetuals) · [`Info.meta_and_asset_ctxs` / `Info.all_mids`](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/info.py)
- `l2Book` takes the fully qualified `coin` value (`bart:AAPL`), not a dex parameter. The bot uses the current best bid and ask to filter any proposed ALO level that would cross. [L2 book docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint#l2-book-snapshot) · [`Info.l2_snapshot`](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/info.py)
- On 2026-09-22 20:35 UTC, the live market maker started with zero existing `bart:AAPL` orders in its account's `openOrders`; it then placed 10 bids and 10 asks with `HLMM` client IDs. Current startup takeover and later re-quotes modify selected-market orders in place and reconcile through `openOrders`; surplus cancellations are filtered to `dex="bart"` and `coin="bart:AAPL"`. It never queries or modifies the `xyz` position. The live trader uses a separate account and can trade against the maker's resting quotes.

## Price precision, ALO, and client IDs

- Perp prices allow up to five significant figures and no more than `6 - szDecimals` decimal places; size precision is `szDecimals`. With current `szDecimals: 2`, sizes are in 0.01 lots. The tick implied by both rules around $39.84 is $0.001. [Tick and lot size docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/tick-and-lot-size)
- The bot uses `order_type={"limit": {"tif": "Alo"}}`. It filters crossing levels against L2 and reallocates the side's target notional over the remaining valid prices. Re-quotes update existing orders through `batchModify`, then add missing levels or cancel surplus levels, preserving the book while the ladder refreshes. Per-order errors are logged and reconciled via `openOrders`. [Exchange endpoint / order schema](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint#place-an-order) · [`Exchange.bulk_orders`](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/exchange.py)
- Optional `--fixed-bid` and `--fixed-ask` pin the nearest level, then step further levels away using the configured bps span. Both must be passed together. Fixed-price mode disables oracle-move re-quotes and retains the timer re-quote. To avoid the observed `Price too far from oracle` rejection, every level is clamped directionally to a 10% band: bids no higher than `oraclePx * 1.10`, asks no lower than `oraclePx * 0.90`. This conservative operational limit matches the observed testnet behavior (with oracle 39.852, bid 43.83 was accepted and 43.87 rejected); it is not inferred as a universal exchange guarantee. Each clamp is logged; price levels are then checked for ALO crossing.
- Each bot order carries a 128-bit client order ID beginning `0x484c4d4d` (ASCII `HLMM`), followed by random bytes. Hand-placed orders with no `cloid` are still cancelled at startup because the bot explicitly takes over every order for this wallet and market.
- Current maker defaults request 20 prices per side between 2 and 25 bps from oracle, targeting $2,000 on each side. The live target is capped from shared Spot free USDC, available Bart margin, current active leverage, and a `$2,500` free USDC reserve. The collateral budget conservatively allows both sides to reserve initial margin simultaneously. Prices are rounded outward from the reference and checked against the live opposite best level before submission. Every poll checks `openOrders`; when either side falls below 70% of its guarded target, the script logs `REFILL_TRIGGER`. Timer, >5 bps oracle movement, and liquidation-risk triggers remain active. At liquidation distance <10%, the maker first adds isolated margin to target at least 15% distance when free Spot USDC above reserve allows; otherwise it preserves full size on the risk-reducing side and cuts the risk-increasing side to 10%. Positions below `$500` notional are exempt from this guard.
- The testnet exchange rejects orders below `$10` notional. The liquidation-reduced `$200` side is split across 20 levels by rounding each level up to its minimum valid `szDecimals` lot; its actual resting total can exceed `$200` slightly. The refill check uses the liquidation-adjusted target, including this risk skew.
- `updateIsolatedMargin` uses the SDK's `Exchange.update_isolated_margin(amount, coin)` action; a positive USDC amount adds margin to that isolated position. The bots estimate the amount needed to place liqPx 16% from oracle, preserve the configured free-USDC reserve, and re-read the position to verify at least 15% distance. If the required amount exceeds free USDC above reserve or the action/verification fails, the maker skews quotes and the trader flattens reduce-only. The maker skips this adjustment/skew for positions below `$500` notional. [Update isolated margin API](https://hyperliquid.gitbook.io/Hyperliquid-docs/for-developers/api/exchange-endpoint#update-isolated-margin) · [SDK example](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/examples/basic_leverage_adjustment.py)

## Collateral and active capacity

- This wallet uses `unifiedAccount`; the official docs say that under unified or portfolio margin, individual perp DEX `clearinghouseState` values are not meaningful for total trading balance, and the Spot balances endpoint is the account-wide balance source. USDC in that unified balance collateralizes cross-margin positions. [Account abstraction modes](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/account-abstraction-modes) · [Perpetuals info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/perpetuals)
- `activeAssetData` returns `availableToTrade` and a leverage object. For the Bart AAPL account, multiplying each available collateral amount by the active leverage cross-checks against `maxTradeSzs * markPx`. The maker preflight requires notional capacity for `2 * per_side_target + position_guard`, and reduces the per-side target to the largest whole-dollar amount that fits if needed. [Active asset data](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint/perpetuals#retrieve-users-active-asset-data)
- The 2026-09-22 21:21 UTC balance/position figures were a historical snapshot and are no longer a reliable live state. `status.py` queries current Spot total/hold/free balances, current position and liquidation distance. The maker recalculates collateral capacity at each quote using live leverage; general insufficient-margin rejects retain existing quotes and back off, while margin-tier rejects trigger leverage acknowledgement and one retry.

## Shared Spot USDC transfers

- `rebalance.py` defines free USDC as Spot `total - hold`. It logs per-DEX `withdrawable` but does not use that field as available collateral for unified accounts. It also reads `activeAssetData.availableToTrade` for `bart:AAPL` and will transfer no more than that remaining margin availability or the donor's amount above its configured minimum.
- For a wallet-to-wallet Spot USDC transfer, the script uses `Exchange.send_asset` with `sourceDex="spot"`, `destinationDex="spot"`, and the dynamically resolved `USDC:<tokenId>`. The generalized `sendAsset` action supports transfers among Spot, perp DEXes, users, and subaccounts; on testnet its signed action uses `hyperliquidChain: "Testnet"`. `spotSend` is disabled when unified-account mode is active, while `usdClassTransfer` moves USDC only between one wallet's Spot and perp accounts. [Exchange endpoint docs](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint) · [SDK `send_asset`](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/exchange.py)
- Corrected rebalancer defaults: maker minimum `$2,500`, trader minimum `$1,500`, target twice each minimum, maximum transfer `$2,000`, and 120-second cooldown. If neither wallet is below its minimum, it does not transfer; if both are below, it logs the faucet warning and does not transfer.

## Separate periodic trader

`trader.py` uses the separate `TEST_HYPERLIQUID_TRADER_PRIVATE_KEY` account on `bart:AAPL`. Defaults are clipped log-normal `$10–$400` IOC clips (median `$40`) and a 30-second mean arrival interval with exponential gaps. About 10% of parent arrivals expand into bursts of 2–5 trades with 1–8-second gaps. Quiet/normal/busy regimes switch every 5–20 minutes at `0.3x`/`1x`/`2.5x` rates, with stationary weights calibrated to an average `1x` rate. Directional side persistence is 65%; 20% of eligible sizes round to human contract counts of 1, 2, 5, or 10 AAPL. Reduce-only flatten cycles remain random 3–12 orders; the `$15,000` position guard and liquidation-margin safety remain active. `--dry-run --simulate-minutes N --seed S` reports size buckets, rates per regime, flatten turnover, and projected daily fees without loading a signing key. The fee guard measures both wallets' configured trailing `--fee-window-hours` (default 2) and scales to a projected daily fee rate. `userFillsByTime` supplies fill `fee` and `feeToken`, with at most 2,000 fills per response and 10,000 recent fills available; fee queries subdivide time windows to avoid the per-response cap. [Info endpoint](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint#retrieve-a-users-fills-by-time) · [Order types](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/order-types) · [SDK `Exchange.order`](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/exchange.py)

The trader account reports `unifiedAccount` abstraction. Its configured $15,000 position cap may exceed the current collateral-supported cap, so it uses the smaller supported limit based on shared Spot USDC, live market leverage, and 90% reserve, and caps risk-increasing clips to remaining headroom. The 10-minute combined fee guard measures both wallets' trailing `--fee-window-hours` (default 2) of USDC fees and scales that observation to a projected daily rate. It proportionally stretches the 30-second base interval above the `$250` daily budget and pauses at more than `$375`, resuming once the projected rate falls to `$250` or lower. If fee data is unavailable or a non-USDC fee token is encountered, it pauses rather than spend against an incomplete USD estimate.

`status.py` uses the same testnet info endpoint and public wallet addresses to print balances, positions/liquidation distance, L2 visible levels/notional, fees over its matching trailing `--fee-window-hours` window (default 2), the projected daily fee rate, and projected runway. It avoids a separate 24-hour fill scan and does not load keys or sign actions.

`trader.py`, `rebalance.py` and `status.py` hard-code `constants.TESTNET_API_URL` (`https://api.hyperliquid-testnet.xyz`) and provide no mainnet endpoint flag. `mm.py` takes `--network testnet|mainnet`; mainnet uses `constants.MAINNET_API_URL`, the `mkts:BVIV` market (on 2026-10-09 `mkts` was perp DEX index 9 and BVIV market index 23, so asset ID `190023`; both are resolved at runtime) and only the `HYPERLIQUID_PRIVATE_KEY` key name. [SDK constants](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/utils/constants.py)

## Collateral by account mode

`userAbstraction` reports the account mode: `unifiedAccount`, `portfolioMargin` or `default` (standard) in practice. Unified and portfolio-margin accounts hold HIP-3 collateral in the Spot USDC balance; standard accounts keep "separate DEX balances", so `mm.py` reads that DEX's `clearinghouseState.withdrawable` instead. Other modes are refused at startup. [Account abstraction modes](https://hyperliquid.gitbook.io/hyperliquid-docs/trading/account-abstraction-modes)
